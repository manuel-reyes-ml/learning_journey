How a SQL Query Actually Runs

One query that uses every clause — FROM, JOIN, WHERE, CASE, GROUP BY, aggregates, HAVING, window functions, SELECT, DISTINCT, ORDER BY, LIMIT — traced step by step on a small dataset, so you can watch the rows change at every stage. Every idea comes in two layers: a plain-terms explanation, then the technical detail, plus notes on how the same logic ships in production.

1 · The scenario: distribution mix by category and plan type

Business question: “For distributions paid in 2026, how many and how much did we pay in each distribution category, by plan type? Keep only combinations with at least $10,000 paid, show each one's share of the distribution count and its rank by dollars, and give me the top 3.”

The query

SELECT
    CASE WHEN d.dist_code IN ('1', '2') THEN 'Early'
         WHEN d.dist_code = '7'        THEN 'Normal'
         WHEN d.dist_code = 'G'        THEN 'Rollover'
         ELSE 'Other' END                    AS dist_category,
    p.plan_type,
    COUNT(*)                                     AS n_dists,
    SUM(d.gross_amount)                          AS total_gross,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1)
                                                 AS pct_of_dists,
    RANK() OVER (ORDER BY SUM(d.gross_amount) DESC)
                                                 AS gross_rank
  FROM distributions AS d
  JOIN plans AS p
    ON p.plan_id = d.plan_id
 WHERE d.status = 'PAID'
   AND d.paid_date >= DATE '2026-01-01'
 GROUP BY 1, 2
HAVING SUM(d.gross_amount) >= 10000
 ORDER BY gross_rank, dist_category
 LIMIT 3;
Plain terms
“Match each distribution to its plan. Keep only the ones paid this year. Label each by type using its 1099-R code. Make one pile per label and plan type, count and total each pile, drop piles under $10K, then work out each pile's share and rank, sort, and show me the top 3.”
Technically
SQL is declarative: you describe the result, not the steps. The engine turns the text into a logical plan (what the answer must be, in the order in section 2) and an optimizer picks a physical plan (the cheapest way to compute it, section 7). They often run in a different order — the optimizer is allowed to reorder anything as long as the result is identical to the logical order.
Data note
All data here is synthetic. The codes follow IRS Form 1099-R box 7: 1 early (no known exception), 2 early (exception applies), 7 normal, G direct rollover, 4 death. Mapping 1 and 2 to “Early” is a simplification for the example.

2 · Written order vs logical order

You write SQL like a sentence, starting with what you want. The engine evaluates it like a recipe, starting with the ingredients. The counts on the right are the rows (or groups) alive after each step in this example.

Order you write it

DISTINCToptional, written as SELECT DISTINCT
FROMfirst table
JOIN … ONsecond table + match rule

GROUP BYgrouping keys

4

5

LIMIT 3keep the first 34 → 3 rows
Why CASE is step 3, and windows are step 7
Plain terms: you can't sort things into piles by a label until the label exists, so the CASE label is computed before grouping. And a window function like “share of the total” needs the piles already counted and filtered, so it comes after HAVING.
Technically: GROUP BY 1 resolves to the CASE expression, and the binder substitutes that expression into the grouping key, so it is evaluated per input row before grouping. Window functions are evaluated after grouping, aggregation and HAVING in their query block, which is why they can wrap an aggregate (SUM(COUNT(*)) OVER ()) and why they can only appear in SELECT and ORDER BY. Microsoft's docs and Itzik Ben-Gan fold windows into the SELECT phase (“evaluate expressions”); Snowflake and most tutorials list them as a separate step between HAVING and SELECT. Same meaning, different bookkeeping.

3 · Step-by-step walkthrough

Click a step or use the ← → keys. Green rows survive, red rows are removed, and blue-tinted columns are new at that step. Every table below was produced by running the query in DuckDB 2.0.

1
FROM distributions AS d JOIN plans AS p ON p.plan_id = d.plan_id
Plain terms
Put the two tables side by side and staple each distribution to its plan, so every row also knows its plan type. An inner join only keeps rows that found a partner. D10 says its plan is P4, there is no P4, so D10 is silently left out. No error, no warning.
Technically
FROM defines the input relation. Logically, a join starts from the cartesian product (16 × 3 = 48 pairs) and keeps the pairs where ON is TRUE. Physically, no engine builds those 48 pairs: it uses a hash join, building a lookup table on the smaller side (plans) and probing it with each distribution. The binder also checks the catalog here: the tables exist, you have SELECT privilege, and every column reference is unambiguous. The aliases d and p are range variables; they exist from this step on, which is why every later clause can say d.status.

2
WHERE d.status = 'PAID' AND d.paid_date >= DATE '2026-01-01'
Plain terms
A checkpoint that looks at one row at a time and asks a yes/no question. Yes → the row continues. No, or “can't tell” → the row is gone for good. It only sees single rows, so it can't ask about counts or totals; those don't exist yet.
Technically
WHERE is a row-level predicate evaluated with three-valued logic (TRUE / FALSE / UNKNOWN). Only TRUE survives. D07's paid_date is NULL, so NULL >= DATE '2026-01-01' is UNKNOWN; even if its status were PAID, it would still be dropped. FALSE AND UNKNOWN is FALSE, so D07 fails on two counts. Optimizers push WHERE as close to storage as possible (predicate pushdown); section 7 shows DuckDB applying this filter inside the table scan, before the join.

3
CASE WHEN … THEN … ELSE … END AS dist_category
Plain terms
An if / else-if / else chain that runs on each surviving row. It checks conditions top to bottom, stops at the first true one, and uses ELSE if nothing matched. The result is a brand-new column that doesn't exist in the table.
Technically
A searched CASE is a scalar expression (one row in, one value out), not a clause. d.dist_code IN ('1','2') is shorthand for d.dist_code = '1' OR d.dist_code = '2'. For D13, NULL IN ('1','2'), NULL = '7' and NULL = 'G' are all UNKNOWN, so no WHEN fires and the row falls to ELSE. That lumps a missing code in with a real, unmapped one (D11, code 4). Every THEN branch must return a compatible type; without an ELSE, unmatched rows get NULL.
# The same logic in Python, to make the evaluation order obvious
def dist_category(code):
    if code in ("1", "2"): return "Early"      # checked 1st
    elif code == "7":      return "Normal"     # only if the 1st was false
    elif code == "G":      return "Rollover"
    else:                  return "Other"      # fallback, catches None and "4"

4
GROUP BY 1, 2
Plain terms
Collect rows with the same category and plan type into one pile. 12 rows become 8 piles. From here on, the engine thinks in piles, not rows: you can only output a pile's label or a summary of it. “The pile's dist_id” has no single answer when the pile holds three distributions.
Technically
GROUP BY partitions the rows by the grouping key (dist_category, plan_type) and changes the grain of the result to one row per distinct key. 1, 2 are ordinals pointing at the 1st and 2nd SELECT items. From here the single-value rule applies: every SELECT item must be a grouping key, an aggregate, a constant, or a window function over those. Engines use a hash aggregate (a hash table keyed on the group, updated as rows stream in; best for few groups) or a sort aggregate (sort by key, emit a group when the key changes; chosen for pre-sorted input or too many groups for memory).

5
COUNT(*) AS n_dists · SUM(d.gross_amount) AS total_gross
Plain terms
For each pile, count the rows and add up the dollars. Each pile now carries two numbers.
Technically
An aggregate keeps a small state per group (a counter, a running sum). Each incoming row runs a transition step, and when input ends a finalize step emits the value. Memory stays tiny: 12 rows or 12 billion, you still hold 8 counters and 8 sums. In parallel engines each worker builds partial aggregates that are combined at the end. COUNT(*) counts rows; SUM ignores NULLs, and returns NULL (not 0) for a group whose values are all NULL.

6
HAVING SUM(d.gross_amount) >= 10000
Plain terms
WHERE's twin for piles. It looks at each pile, now that the totals exist, and throws out the piles under $10,000. Four piles survive.
Technically
HAVING is a group-level predicate: it runs after aggregation and can reference aggregates, including ones not in the SELECT list. Standard SQL doesn't let it reference the SELECT alias total_gross (that's born later, in step 8), so the aggregate is repeated. PostgreSQL and SQL Server reject the alias; DuckDB, Snowflake, BigQuery and MySQL accept it as an extension.

Production note
Row conditions belong in WHERE (filter early, before the expensive grouping). Only conditions on aggregates belong in HAVING. HAVING d.status = 'PAID' is either invalid or wasteful, because the engine would aggregate rows only to discard them.
7
SUM(COUNT(*)) OVER () · RANK() OVER (ORDER BY SUM(d.gross_amount) DESC)
Plain terms
Now that the 4 surviving piles exist, look across them without merging them. SUM(COUNT(*)) OVER () adds up the piles' counts (3 + 1 + 1 + 2 = 7) and writes that grand total next to every pile, so each pile can work out its share. RANK() lines the piles up by dollars and numbers them 1, 2, 3, 4.
Technically
A window function computes over a set of rows related to the current row and, unlike GROUP BY, does not collapse rows: 4 rows in, 4 rows out. Here it runs on the grouped, HAVING-filtered result, so its inputs are the aggregates. In SUM(COUNT(*)) OVER () the inner COUNT(*) is the step-5 aggregate (one value per group) and the outer SUM … OVER () is the window. An empty OVER () means one window holding every row, with no ordering. In RANK() OVER (ORDER BY SUM(d.gross_amount) DESC), the window's own ORDER BY only decides the ranking; it does not sort the output (that's step 10).

Why you can't filter on a window in WHERE or HAVING
Both run before step 7, so the window value doesn't exist yet. WHERE gross_rank <= 3 or HAVING RANK() OVER (…) = 1 are errors. Compute the window in a CTE and filter in the next one (portable), or use QUALIFY in DuckDB, Snowflake, BigQuery and Databricks, a filter that runs right after the windows.
8
SELECT … AS dist_category, plan_type, n_dists, total_gross, pct_of_dists, gross_rank
Plain terms
Lay out the answer: which columns appear, in what order, and what they're called. AS is just a name tag. Helper values (the 7) are used inside an expression but don't get their own column unless you ask for one.
Technically
This is the projection: evaluate the output expressions per row and assign column aliases. Aliases are born here, which is why WHERE, HAVING and (in strict engines) GROUP BY can't see them, while ORDER BY can. ROUND(…, 1) is applied here too. Order is still undefined: a hash aggregate emits groups in hash-table order, which can change between runs, versions and data sizes.

9
DISTINCT (not in this query)
Plain terms
DISTINCT removes duplicate output rows. This query doesn't need it: GROUP BY already guarantees one row per category and plan type, so no two output rows can be identical.
Technically
DISTINCT runs on the projected rows, after SELECT and before ORDER BY. It's implemented with the same machinery as GROUP BY (a hash aggregate on every output column). When it does run, ORDER BY can only use columns that are in the SELECT list (PostgreSQL enforces this), because after duplicates collapse, a hidden column no longer has a single value per row.
Code smell
SELECT DISTINCT on top of a join or GROUP BY often hides a bug: the join fanned out (one row matched several) and DISTINCT throws the copies away after the engine did the work. If you need DISTINCT to make the numbers look right, find out why the duplicates exist. Section 13 shows a self join where EXISTS replaces DISTINCT.
Row count: 4, unchanged.
10
ORDER BY gross_rank, dist_category
Plain terms
Sort the final rows by rank. If two rows ever tie on rank, sort those by category name so the order is always the same.
Technically
ORDER BY runs after SELECT, so it can use aliases (gross_rank) and window results. The second key is a tie-breaker: RANK() gives tied rows the same number, and without a deterministic tie-breaker their order can change from run to run. That makes snapshot tests and diffs flaky. It's the only clause that guarantees row order.

11
LIMIT 3
Plain terms
Keep the first 3 rows of the sorted list and throw away the rest. This is the very last thing that happens.
Technically
LIMIT (SQL Server: TOP; standard: FETCH FIRST n ROWS ONLY) only trims the output. Everything earlier, including the window functions, already saw all 4 rows. Without ORDER BY, LIMIT returns an arbitrary 3. Engines usually fuse ORDER BY + LIMIT into a single top-N operator that keeps only the best N in memory instead of sorting everything (DuckDB's plan shows Top N).

5 · Syntax notes

CASE: two forms

-- Searched CASE: any condition per branch (used here)
CASE WHEN dist_code IN ('1','2') THEN 'Early'
     WHEN gross_amount >= 50000  THEN 'Large'
     ELSE 'Other' END

-- Simple CASE: one expression compared with =
CASE dist_code WHEN '7' THEN 'Normal'
               WHEN 'G' THEN 'Rollover'
               ELSE 'Other' END

Simple CASE can't match NULL: it compares with =, and NULL = NULL is UNKNOWN. Use the searched form with WHEN dist_code IS NULL. CASE also works inside aggregates (conditional aggregation): SUM(CASE WHEN dist_code = 'G' THEN gross_amount END) gives rollover dollars in the same pass. Many engines also support the cleaner COUNT(*) FILTER (WHERE …) (PostgreSQL, DuckDB).

Aggregate vs window: same function, different shape

ExpressionRows outPlain terms
SUM(x) + GROUP BYone per group“Total per pile”
SUM(x) OVER ()one per input row“Grand total next to every row”
SUM(x) OVER (PARTITION BY k)one per input row“Subtotal of my pile, next to me”
SUM(x) OVER (ORDER BY t)one per input row“Running total up to me”
SUM(COUNT(*)) OVER ()one per group“Total of all piles' counts, next to every pile”

Nesting rule: a window may wrap an aggregate (SUM(COUNT(*)) OVER ()), but an aggregate may never wrap a window (SUM(RANK() OVER …) is an error), and aggregates can't nest directly (SUM(COUNT(*)) without OVER is an error).

Anatomy of OVER (…)

function(args) OVER (
    PARTITION BY plan_type                              -- 1. split rows into independent windows (omit = one window)
    ORDER BY SUM(gross_amount) DESC                     -- 2. order rows inside each window (needed by RANK, LAG, running totals)
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW    -- 3. frame: which ordered rows the function sees
)

Plain terms: PARTITION BY decides “who's in my group,” ORDER BY decides “who comes before me,” and the frame decides “how far back (or forward) I look.”

Default frame trap: with ORDER BY and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Rows that tie on the ORDER BY value are peers and get the same running total. Write ROWS … explicitly when you want strictly row-by-row behavior.

Ranking functionTiesExample on 100, 90, 90, 80
ROW_NUMBER()broken arbitrarily1, 2, 3, 4

Use ROW_NUMBER() for deduplication (“latest record per participant”) with a full tie-breaker, so exactly one row wins.

Alias scope: who can see total_gross?

Follow the logical order. The alias is created at step 8, so only steps after it can see it in standard SQL: ORDER BY total_gross works everywhere; WHERE, HAVING and GROUP BY are dialect-dependent (section 9). The table aliases d and p are created in FROM, so every clause can see them. For portable code, either repeat the expression or compute it in a CTE and reference the column in the next CTE.

STAGE 3
Rewriter

Normalizes the tree: expands views, rewrites IN, folds constants, inlines CTEs and subqueries.

STAGE 4
Optimizer / Planner

Estimates costs from statistics and picks join order, join algorithm, scan type, aggregate and sort strategy.

STAGE 5
Executor

Runs the operators and streams rows or batches up through scan → join → aggregate → filter → window → sort/limit.

How the optimizer decides

Plain terms: it estimates “how many rows survive each step?” and picks the cheapest route. Filtering 1,000 paid distributions before joining is cheaper than joining 1,000,000 and filtering afterwards, so it moves WHERE below the join.

Technically: cost-based optimization uses column statistics (histograms, distinct counts, null fraction) collected by ANALYZE (PostgreSQL) or automatically (Snowflake, BigQuery, DuckDB) to estimate selectivity. It chooses the build side of a hash join (the smaller input), pushes predicates down, and prunes unused columns. Stale statistics give bad estimates, and bad estimates give bad plans.

How windows are executed

Plain terms: to rank piles, the engine has to line them up first. To compute a grand total, it reads every pile once and broadcasts the sum back.

Technically: the Window operator (PostgreSQL WindowAgg) needs its input sorted by PARTITION BY, then ORDER BY. Windows with the same OVER (…) share one sort, so reuse identical window definitions (or a named WINDOW w AS (…)). An empty OVER () needs no sort, just one pass. Large partitions are the window equivalent of a hash spill: memory-hungry and slow.

Columnar storage

Plain: read only the columns you asked for.
Tech: this query reads 5 of 7 distribution columns and 2 of 3 plan columns. On wide warehouse tables, that's why SELECT * is expensive.

Pruning

Plain: skip whole chunks that can't contain a match.
Tech: if a block's max paid_date is in 2025, paid_date >= '2026-01-01' can't match anything in it, so it's skipped unread. Partitioning or clustering on paid_date makes this very effective.

Parallelism & spill

Plain: split work across CPU cores, then merge.
Tech: partial hash aggregates per thread are combined at the end. If a hash table or sort outgrows memory (work_mem in PostgreSQL), it spills to disk and slows down.

Row-at-a-time vs vectorized
PostgreSQL uses the classic Volcano / iterator model, where each operator pulls one tuple from its child. DuckDB uses vectorized, push-based execution on batches of 2,048 values, organized in row groups of 122,880 rows that carry min/max metadata for skipping. Snowflake, BigQuery, ClickHouse and Polars use variants of the same idea.

Logical vs physical, side by side
WHERE runs before the JOIN. Logically the join comes first (step 1). Physically, the optimizer pushed the WHERE filter into the scan of distributions, so only paid 2026 rows are ever joined. Same result, less work.

Only needed columns travel. status and paid_date are used inside the scan filter and then dropped; dist_id and participant_id are never read at all.

ORDER BY and LIMIT become one operator. “Top N” keeps the best 3 rows in a small heap instead of sorting all of them.

Everything else matches the logical order exactly: CASE before grouping, HAVING as a filter on aggregates, windows after HAVING.
What to look for in EXPLAIN ANALYZE
Estimated vs actual rows on each node: a 10× gap means stale statistics or a predicate the optimizer can't estimate. A join whose output is much larger than its inputs means fan-out. A sequential scan of a huge table with a selective filter suggests a missing index, poor partitioning, or a non-sargable predicate. Spill / “Disk” / Batches > 1 on a hash or sort node means it ran out of memory.

8 · Semantics & edge cases (the ones that bite in production)

1 · Inner joins drop orphans silently
D10 (plan P4) disappeared at step 1 with no error: 16 source rows became 15. Decide on purpose. Use INNER JOIN when an orphan is genuinely out of scope, and LEFT JOIN plus a COALESCE(p.plan_type, 'Unknown plan') when it must still be counted. Either way, add a relationships test so orphans are reported, not hidden. (Verified: the LEFT JOIN returns all 16 rows, with D10's plan_type NULL.)
2 · NULL means “unknown”, and unknown fails every filter
D07's NULL paid_date makes paid_date >= … UNKNOWN, and WHERE keeps only TRUE. In CASE, D13's NULL code made every WHEN UNKNOWN, so it landed in ELSE next to a real code (D11, code 4). Put WHEN dist_code IS NULL THEN 'Unknown' first, so missing data is visible instead of blended into “Other”.
3 · Dirty values miss every branch
'g' is not 'G', and ' 7' is not '7'. Verified on this dataset: adding one 'g' row ($11,000) and one ' 7' row ($9,000) sends both to “Other” with no error. After upper(trim(dist_code)) they move to Rollover · 403(b) and Normal · 457(b). Normalize once in a staging model, not inside every query.
4 · CASE is first-match-wins
A broad rule above a narrow one starves it: put WHEN gross_amount >= 10000 THEN 'Large' first and no large rollover is ever labeled “Rollover”. Order branches from most specific to most general.
5 · COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)
ExpressionCountsPlain terms
COUNT(*) / COUNT(1)every row in the group“How many rows?”
COUNT(dist_code)rows where dist_code IS NOT NULL“How many rows have a value here?” (D13 wouldn't count)
COUNT(DISTINCT participant_id)unique non-null values“How many different participants?”
6 · HAVING shrinks the window's denominator; LIMIT doesn't
Because windows run after HAVING, SUM(COUNT(*)) OVER () was 7, not 12. Because they run before LIMIT, the shares shown in the final 3 rows add up to 85.8%, not 100%. Decide which denominator the business means (“share of all paid distributions” vs “share of material groups”) and make the query express that, usually by computing the share in one CTE and filtering in the next.
7 · Integer division depends on the engine
COUNT(*) / SUM(COUNT(*)) OVER () returns different things by dialect. SQL Server: both sides are int, so it truncates to 0. PostgreSQL: sum(bigint) returns numeric, so this specific expression is safe, but COUNT(*) / COUNT(*)-style integer math truncates. DuckDB: / always returns a decimal fraction and // is integer division (verified: 0.1667 vs 0). Habit: write 100.0 * … or cast explicitly, so the result never depends on the engine.
8 · Ties make output non-deterministic
If two groups had the same total, RANK() would give both the same number and their order would be up to the engine. Always end ORDER BY with a unique tie-breaker, and use ROW_NUMBER() with a full ORDER BY when exactly one row must win.
9 · Non-sargable filters disable indexes and pruning
WHERE paid_date >= '2026-01-01' AND paid_date < '2027-01-01' is index- and pruning-friendly. WHERE EXTRACT(YEAR FROM paid_date) = 2026 and WHERE CAST(paid_date AS TEXT) LIKE '2026%' force a calculation on every row first.
10 · No ORDER BY = no guaranteed order
Results that “always came back sorted” in development can change when data grows, the engine upgrades, or the plan goes parallel. Any test, export or diff that depends on row order needs an explicit ORDER BY.

Pattern B · Layered CTEs that read in logical order

Plain: each CTE is one logical step from section 3, with a name. To debug, change the last line to select * from <any step> and look at the rows at that point.
Tech: dbt Labs' convention is import CTEs, then logical CTEs, then select * from final. Modern optimizers inline CTEs (PostgreSQL ≥ 12 by default, DuckDB too), so this costs nothing at runtime.

models/marts/distribution_mix_by_category.sql

{% set start_date = var('dist_mix_start_date', '2026-01-01') %}
{% set materiality_usd = var('dist_mix_materiality_usd', 10000) %}

with distributions as (                                   -- import CTEs
    select * from {{ ref('stg_recordkeeper__distributions') }}
),

plans as (
    select * from {{ ref('stg_recordkeeper__plans') }}
),

code_map as (
    select * from {{ ref('dist_code_category_map') }}
),

paid as (                                                 -- step 2: WHERE, filter early
    select *
    from distributions
    where dist_status = 'PAID'
      and paid_date >= cast('{{ start_date }}' as date)
),

classified as (                                           -- steps 1 + 3: JOIN + label
    select
        paid.dist_id,
        paid.gross_amount_usd,
        coalesce(plans.plan_type, 'Unknown plan') as plan_type,   -- LEFT JOIN keeps orphans
        case
            when paid.dist_code is null then 'Unknown'
            else coalesce(code_map.dist_category, 'Other')
        end as dist_category
    from paid
    left join plans    on paid.plan_id   = plans.plan_id
    left join code_map on paid.dist_code = code_map.dist_code
),

grouped as (                                              -- steps 4-5: GROUP BY + aggregates
    select
        dist_category,
        plan_type,
        count(*)              as n_dists,
        sum(gross_amount_usd) as total_gross_usd
    from classified
    group by 1, 2
),

final as (                                                -- step 7: windows over ALL groups
    select
        dist_category,
        plan_type,
        n_dists,
        total_gross_usd,
        round(100.0 * n_dists / sum(n_dists) over (), 1)            as pct_of_paid_dists,
        rank() over (order by total_gross_usd desc, dist_category, plan_type) as gross_rank,
        total_gross_usd >= {{ materiality_usd }}                    as is_material
    from grouped
)

select * from final
Three deliberate differences from the ad-hoc query
1. The aggregate and the window live in separate CTEs, so sum(n_dists) over () replaces the nested SUM(COUNT(*)) OVER (): same result, easier to read. 2. The share is computed over all groups, so its name (pct_of_paid_dists) is true, and the HAVING became an is_material flag the dashboard can filter on. 3. The rank's ORDER BY includes tie-breakers, so it's deterministic.

12 · Recall & practice

From/Join → Where → Group by → Having → Window → Select → Distinct → Order by → Limit
“Friendly Joins Wait; Groups Have Windows; Select Distinct Orders Last.” Rows are filtered before groups, groups before windows, windows before output, output before sorting and limiting.

Easy

Why does ORDER BY gross_rank work in every engine, while HAVING total_gross >= 10000 fails in PostgreSQL? Answer with the logical order table.

Answer: the alias is born at SELECT (step 8). ORDER BY runs after it; HAVING runs before it.

Medium

Change the HAVING to COUNT(*) >= 2. Predict which groups survive, the new denominator, and the final 3 rows before you run it.

Answer (verified): denominator 7 · Rollover 457(b) 2 · 28.6 · rank 1 · Normal 403(b) 3 · 42.9 · rank 2 · Early 403(b) 2 · 28.6 · rank 3.

Hard

Return the top category per plan type by dollars, one row per plan type. Write it twice: with a CTE + WHERE rnk = 1 (portable) and with QUALIFY (DuckDB). Compare the plans.

Answer (verified): Normal · 403(b) · 33,000 and Rollover · 457(b) · 45,000. Hint: RANK() OVER (PARTITION BY p.plan_type ORDER BY SUM(d.gross_amount) DESC).

13 · Self joins: comparing a table with itself

Question: which companies received a Japanese investment and then, later, a British investment? Both events live in the same table, so the query joins the table to itself.

SELECT DISTINCT japan_i.company_name,
                japan_i.company_permalink
FROM tutorial.crunchbase_investments_part1 AS japan_i
JOIN tutorial.crunchbase_investments_part1 AS gb_i
  ON japan_i.company_name = gb_i.company_name
  AND gb_i.investor_country_code = 'GBR'
  AND gb_i.funded_at > japan_i.funded_at
WHERE japan_i.investor_country_code = 'JPN'
ORDER BY 1;
Plain terms
A single row only knows about itself. It can't say “this same company got British money later.” So you photocopy the list, label one copy japan_i and the other gb_i, lay them side by side, and look for pairs of rows that fit your rules. Each surviving pair is one piece of evidence: “this Japanese round, followed by that British round.”
Technically
Nothing is copied. The aliases are two range variables over the same relation, and the planner gives each one its own scan. Aliases are mandatory here: without them every column (company_name, funded_at) is ambiguous. Logically, a join starts from the cartesian product (11 × 11 = 121 pairs on the sample) and keeps the pairs where ON is TRUE. Physically, the engine never builds those 121 pairs (see the plan below).

Step 1 · Two views of the same table

Plain: each copy is narrowed to the rows it cares about. The left copy keeps only Japanese rounds, the right copy only British rounds.
Tech: the optimizer pushes WHERE japan_i.investor_country_code = 'JPN' into the left scan and the ON … gb_i.investor_country_code = 'GBR' condition into the right scan (predicate pushdown). Both sides are small before any pairing happens.

Step 4 · What the engine actually ran

Plain: instead of comparing every row with every row, the engine files the British rounds in a lookup index by company. Each Japanese round looks up its company, checks the dates, and moves on.
Tech: a hash join. Read bottom-up:

HASH_GROUP_BY   Groups: company_name, company_permalink   ← DISTINCT (same machinery as GROUP BY)
  HASH_JOIN  INNER
    Conditions: company_name = company_name              ← hashed equi-join key
                funded_at < funded_at                      ← residual check on each key match
    SEQ_SCAN  Filters: investor_country_code='JPN'        ← japan_i (pushed-down WHERE)
              Projections: company_name, funded_at, company_permalink
    SEQ_SCAN  Filters: investor_country_code='GBR'        ← gb_i (pushed-down ON)
              Projections: company_name, funded_at

Real DuckDB output on the sample, trimmed of internal string-compression projections. DuckDB writes the date check as < because it puts the sides in the opposite order; the meaning is the same. Note the GBR side reads only two columns, since the permalink is needed only from the Japan side.

ON vs WHERE: why it doesn't matter here, and when it does

INNER JOIN: interchangeable · LEFT JOIN: not
Plain: with an inner join, a pair must pass every rule anyway, so it doesn't matter which box a rule sits in. With a left join, the left row is promised a seat even if it has no partner. A rule in ON just means “no partner found,” but the same rule in WHERE throws the row out entirely.
Tech: for LEFT JOIN, ON conditions control matching and WHERE conditions control which rows survive after NULL-padding. Putting gb_i.investor_country_code = 'GBR' in WHERE removes every unmatched row (its gb_i columns are NULL), which silently turns the LEFT JOIN back into an INNER JOIN. 
-- "Every Japan-backed company, plus its first later British round if any"
select japan_i.company_permalink, min(gb_i.funded_at) as first_gbr_after_jpn
from tutorial.crunchbase_investments_part1 as japan_i
left join tutorial.crunchbase_investments_part1 as gb_i
    on  gb_i.company_permalink     = japan_i.company_permalink
    and gb_i.investor_country_code = 'GBR'                 -- must stay in ON
    and gb_i.funded_at             > japan_i.funded_at      -- must stay in ON
where japan_i.investor_country_code = 'JPN'                -- left-side filter: WHERE is correct
group by 1

The production version

Why DISTINCT here is a code smell
Plain: the join produced extra copies of Acme, and DISTINCT throws them away afterwards. You did the work, then threw it away. With real Crunchbase data (dozens of rounds per company), that's a lot of wasted work, and DISTINCT can also hide a join bug that's producing the wrong rows.
Tech: the business question is existential (“does a later GBR round exist?”), not “list every JPN→GBR pair.” Express existence directly with a semi-join (EXISTS), which stops at the first match per left row and never multiplies rows.

Pattern A · EXISTS (semi-join)

select
    japan_i.company_name,
    japan_i.company_permalink
from tutorial.crunchbase_investments_part1 as japan_i
where japan_i.investor_country_code = 'JPN'
  and exists (
      select 1
      from tutorial.crunchbase_investments_part1 as gb_i
      where gb_i.company_permalink     = japan_i.company_permalink
        and gb_i.investor_country_code = 'GBR'
        and gb_i.funded_at             > japan_i.funded_at
  )
group by 1, 2      -- one row per company (Acme had 2 JPN rounds)
order by 1

Best when you need the per-round logic, or later want to switch to NOT EXISTS (“Japan-backed, never British-backed after”), which is the safe anti-join. NOT IN breaks when the subquery returns a NULL.

Pattern B · Conditional aggregation (no join at all)

select
    company_name,
    company_permalink
from tutorial.crunchbase_investments_part1
group by 1, 2
having
    max(case when investor_country_code = 'GBR' then funded_at end)
  > min(case when investor_country_code = 'JPN' then funded_at end)
order by 1

Plain: for each company, find its earliest Japanese date and its latest British date. If the latest British date is after the earliest Japanese one, a qualifying pair must exist.
Tech: one scan and one hash aggregate, no join and no fan-out. Companies missing either side get a NULL, the comparison is UNKNOWN, and HAVING drops them. Verified: returns Acme and Echo on the sample.

Self-join gotchas

1 · Join on a key, not a label
company_name isn't unique: two different companies can share a name, and they'd be paired with each other. Join on the stable identifier (company_permalink). It's the same rule as joining participants on SSN/participant ID, never on name.
2 · A row can match itself
In self joins that compare rows of the same kind (duplicates, same-day events), add a.row_id <> b.row_id. For unordered pairs, use a.row_id < b.row_id, which also stops each pair from appearing twice (A–B and B–A). This query avoids the problem only because the two sides are different countries.
3 · Dates stored as text
If funded_at is a string, > compares alphabetically. That's correct only for ISO YYYY-MM-DD; '1/5/2013' > '12/1/2012' gives the wrong answer. Cast to date in the staging model. Rows with a NULL date silently fail the comparison.
4 · Row explosion
Fan-out grows with JPN rounds × GBR rounds per company. A company with 20 of each makes up to 400 pairs before DISTINCT. Check with EXPLAIN ANALYZE: if the join node's actual row count is far larger than the final result, switch to Pattern A or B.

Classic self-join use cases

Hierarchies

Employee → manager in one employees table: e.manager_id = m.employee_id. Use a LEFT JOIN so the CEO (no manager) isn't lost.

Duplicate detection

Same participant, same amount, same date, different record: a.participant_id = b.participant_id AND a.amount = b.amount AND a.row_id < b.row_id. This is a natural QA check for distribution data.

Sequences of events

“A then B” (this query), or “rollover requested then distribution paid within N days.” Consider Pattern B or LAG first.

Debugging habit
When a join result looks wrong, select both sides' keys and the compared columns without DISTINCT or GROUP BY, the way query 1 above does. Seeing the raw pairs shows fan-out, self-matches and wrong keys immediately.

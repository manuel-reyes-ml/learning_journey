SQL internals · reference

How a SQL Query Actually Runs

The clauses you write, the order the engine evaluates them, what the database does internally to execute them, and how to write the same query to production standard. Every idea comes in two layers: a plain-terms explanation, then the technical detail.

1 · The query

SELECT CASE WHEN state IN ('CA', 'OR', 'WA') THEN 'West Coast'
            WHEN state = 'TX' THEN 'Texas'
            ELSE 'Other' END AS arbitrary_regional_designation,
       COUNT(1) AS players
  FROM benn.college_football_players
 WHERE weight >= 300
 GROUP BY 1
Plain terms
“Take the football-players table. Keep only players who weigh 300 lb or more. Label each one by region based on his state. Then tell me how many players fall under each label.”
Technically
SQL is declarative: you describe the result you want, not the steps to get it. The engine turns your text into a logical plan (what the answer must be), then an optimizer picks a physical plan (the cheapest way to compute it). Those are two different things, and confusing them is the source of most SQL surprises.

2 · Written order vs logical order

You write SQL like an English sentence, starting with what you want. The engine evaluates it like a recipe, starting with the ingredients.

Order you write it

FROMsource table
WHERErow filter
GROUP BY 1grouping key

Order the engine evaluates it

1
FROMget the rows
2
WHEREdrop rows that fail
3
CASE … ENDcompute the group key
4
GROUP BYcollapse rows into groups
5
COUNT(1)aggregate per group
6
SELECT … ASshape & name the output
Why CASE is step 3, not step 6
Plain terms: you can't sort things into piles by a label until the label exists. GROUP BY 1 says “group by the 1st item in my SELECT list,” and that item is the CASE label, so the engine has to compute it before grouping.
Technically: PostgreSQL's docs say output columns are nominally computed after grouping, but GROUP BY may still reference them by name or ordinal. The binder resolves 1 to the CASE expression and substitutes that expression into the grouping key. The rest of SELECT (column naming, final projection) still happens last.

3 · Step-by-step walkthrough

A 12-row sample (made-up values, chosen so every rule fires at least once). Click a step or use ← → keys.

1
FROM benn.college_football_players
Plain terms
Before you can do anything, you need the data in front of you. FROM says which table to read. benn is the schema (think: folder) and college_football_players is the table (think: file in that folder).
Technically
FROM defines the input relation. With JOINs, this step builds the combined row set (logically a cross product filtered by ON, then outer rows added back for LEFT/RIGHT/FULL joins). The binder looks benn.college_football_players up in the system catalog to confirm it exists, that you have SELECT privilege, and what its columns and types are. A columnar engine (Snowflake, BigQuery, DuckDB, Redshift) will only read the columns the query touches: state and weight. This is called projection pushdown.

2
WHERE weight >= 300
Plain terms
A checkpoint that looks at one row at a time and asks a yes/no question. Yes → the row continues. No (or “unknown”) → the row is thrown away for good. Because it only sees single rows, it can't ask anything about groups or counts. Those don't exist yet.
Technically
WHERE is a row-level predicate evaluated with three-valued logic (TRUE / FALSE / UNKNOWN). Only TRUE survives. A row with weight IS NULL gives NULL >= 300 → UNKNOWN and is silently dropped. The optimizer pushes this predicate as close to storage as it can (predicate pushdown). It may use a B-tree index on weight, or skip whole storage blocks whose min/max stats show max(weight) < 300 (zone maps / row-group pruning in Parquet, DuckDB, Snowflake micro-partitions).

3
CASE WHEN … THEN … ELSE … END
Plain terms
An if / else-if / else chain that runs on each surviving row. It checks the conditions top to bottom and stops at the first one that's true. If nothing matches, ELSE is the fallback. The result is a brand-new column that doesn't exist in the table. The engine computes it on the fly.
Technically
This is a searched CASE expression. It's a scalar expression (one row in → one value out), not a clause. state IN ('CA','OR','WA') is shorthand for state = 'CA' OR state = 'OR' OR state = 'WA'; PostgreSQL rewrites it internally as state = ANY('{CA,OR,WA}'). Every THEN branch must resolve to a compatible type (all text here). Without an ELSE, unmatched rows get NULL.
-- Equivalent Python, to make the evaluation order obvious
def region(state):
    if state in ("CA", "OR", "WA"): return "West Coast"   # checked 1st

    else:                          return "Other"        # fallback (remove it → None/NULL)

4
GROUP BY 1
Plain terms
Collect rows with the same label into one pile. 9 rows become 3 piles. From this point on, the engine thinks in piles, not rows. That's why, after grouping, you can only output the pile's label or a summary of the pile (count, sum, average). “The player's name” has no single answer for a pile of three players.
Technically
GROUP BY partitions the row set by the grouping key and changes the grain of the result: one output row per distinct key. The single-value rule applies from here on: every SELECT item must be a grouping key, an aggregate, or a constant. Engines implement this two ways. A hash aggregate builds a hash table keyed on the group value and updates each group's running state as rows stream in; it's best when the number of groups is small, as here. A sort aggregate (PostgreSQL's GroupAggregate) sorts by the key and emits a group each time the key changes; it's chosen when the input is already sorted or there are too many groups to fit in memory.

5
COUNT(1)
Plain terms
For each pile, count the rows in it. COUNT(1) means “add 1 for every row,” so it gives exactly the same answer as COUNT(*).
Technically
An aggregate keeps a small state per group (here a single integer). Each incoming row runs a transition step (state += 1), and once input ends a finalize step emits the value. That's why aggregation is memory-cheap: 9 rows or 9 billion, you still hold just 3 counters. In parallel engines, each worker builds partial aggregates on its share of the data, and the partials are then combined (summing three per-worker counts). COUNT(1) vs COUNT(*) makes no meaningful performance difference in modern engines; COUNT(*) is the conventional spelling.

SELECT … AS …
Plain terms
Lay out the final answer: which columns appear, in what order, and what they're called. AS is just a name tag on a column.
Technically
This is the projection: it evaluates output expressions per group and assigns column aliases. Aliases are born here, which is why WHERE, GROUP BY (in strict engines) and HAVING can't see them, but ORDER BY (step 7) can. With no ORDER BY, row order is undefined. A hash aggregate emits groups in hash-table order, which can change between runs, versions or data volumes.

Window functions — why you can't filter on them in WHERE
Window functions (ROW_NUMBER() OVER (…), SUM(x) OVER (…)) are computed during step 5, after WHERE, GROUP BY and HAVING. So WHERE ROW_NUMBER() OVER (…) = 1 is invalid. The fix is to compute it in a CTE and filter in the next one. Snowflake, BigQuery, DuckDB and Databricks also offer QUALIFY, a filter that runs after window functions.

5 · Inside the engine: from text to result

Plain terms
Section 3 showed what the answer must be. Behind the scenes, a pipeline of components reads your text, checks it, finds the fastest way to compute it, and runs that plan. The optimizer is free to reorder, merge or skip work, but the result must always be identical to what the logical order would produce.
STAGE 1
Parser

Checks the grammar and turns the text into a syntax tree. It doesn't yet know whether the tables exist.

syntax error at or near "FORM"
STAGE 2
Analyzer / Binder

Looks up names in the catalog, resolves types, resolves GROUP BY 1 to the CASE expression, and enforces the single-value rule.

column "wieght" does not exist
STAGE 3
Rewriter

Normalizes the tree: expands views, simplifies IN to = ANY, folds constants, flattens subqueries and CTEs.

STAGE 4
Optimizer / Planner

Generates candidate plans and estimates their cost from table statistics. Picks the scan type, join order and aggregate strategy.

STAGE 5
Executor

Runs the plan's operators and streams rows (or batches) from storage up through filter → project → aggregate.

How the optimizer decides

Plain terms: it estimates “how many rows will survive the filter?” and picks the cheapest route. If only a handful of players weigh 300+, jumping straight to them via an index beats reading every row. If half of them do, reading everything sequentially is faster.

Technically: cost-based optimization uses column statistics (histograms, distinct counts, null fraction) collected by ANALYZE (PostgreSQL) or automatically (Snowflake, BigQuery, DuckDB) to estimate selectivity. Stale statistics give bad estimates, and bad estimates give bad plans. That's why ANALYZE after a large load is a production habit.

Row-at-a-time vs vectorized

Plain terms: an old-style engine passes rows up the plan one at a time, like a single-file line. A modern analytical engine passes a tray of a couple thousand values at once, so the CPU does the same operation on many values in a tight loop.

Technically: PostgreSQL uses the classic Volcano / iterator model, where each operator's next() pulls one tuple from its child. DuckDB uses vectorized, push-based execution: batches of 2,048 values per vector, organized in row groups of 122,880 rows that carry min/max metadata for skipping. Snowflake, BigQuery, ClickHouse and Polars use variants of the same idea.

Columnar storage

Plain: read only the columns you asked for.
Tech: this query touches 2 columns. On a 10-column table, that's roughly 80% less I/O. This is why SELECT * is expensive in a warehouse.

Pruning

Plain: skip whole chunks that can't contain a match.
Tech: if a block's max weight is 280, the filter weight >= 300 can't match anything in it, so it's skipped without being read. Partitioning and clustering on common filter columns makes this work far better.

Parallelism & spill

Plain: split the work across CPU cores, then merge the results.
Tech: partial hash aggregates per thread are merged at the end. If the hash table outgrows memory (work_mem in PostgreSQL), the engine spills to disk and slows down. 3 groups will never come close.

6 · Reading the execution plan

Plain terms: EXPLAIN asks the database to show its plan without running the query. EXPLAIN ANALYZE runs it and shows real timings and row counts. Read plans from the innermost / bottom node up: that's where data enters.

PostgreSQL (illustrative)

HashAggregate                               ← steps 4–5: group + count
  Group Key: CASE
    WHEN (state = ANY ('{CA,OR,WA}'::text[]))  ← step 3: IN rewritten to = ANY
      THEN 'West Coast'::text
    WHEN (state = 'TX'::text) THEN 'Texas'::text
    ELSE 'Other'::text END
  ->  Seq Scan on college_football_players  ← step 1: read table
        Filter: (weight >= 300)              ← step 2: applied during the scan

With a selective filter and an index on weight, Seq Scan becomes Index Scan or Bitmap Heap Scan. With many groups or pre-sorted input, HashAggregate may become Sort → GroupAggregate.

Captured from DuckDB on the sample in section 10. The full output also includes internal string compress/decompress projections and the ORDER BY node, removed here for clarity. Note Projections: state: weight is used only inside the scan filter, so it never travels up the plan.

What to look for in EXPLAIN ANALYZE
Estimated vs actual rows on each node. A 10× or bigger gap means stale statistics or a predicate the optimizer can't estimate. Seq Scan on a huge table with a selective filter often signals a missing index or a non-sargable predicate (see below). “Disk” / “Batches > 1” on a hash node means it ran out of memory and spilled.

7 · Semantics & edge cases (the ones that bite in production)

1 · NULLs take the ELSE branch silently
Plain: a player with a blank state isn't “West Coast,” isn't “Texas,” so he lands in “Other” and gets mixed in with real states.
Tech: NULL IN ('CA','OR','WA') → UNKNOWN, and NULL = 'TX' → UNKNOWN, so the row falls to ELSE. A NULL weight is excluded by WHERE. Either way, nothing errors. If missing data matters, make it explicit: 
CASE WHEN state IS NULL               THEN 'Unknown'   -- first, so it isn't hidden in Other
     WHEN state IN ('CA','OR','WA')   THEN 'West Coast'
     WHEN state = 'TX'                THEN 'Texas'
     ELSE 'Other' END
2 · Dirty values miss every branch
Plain: 'tx', ' TX' and 'Tex.' are not 'TX', so they all become “Other.”
Tech: string comparison is exact (case- and whitespace-sensitive in most engines and collations). Normalize once, upstream, in a staging model with upper(trim(state)). Don't patch it inside every query.
3 · CASE is first-match-wins
Put a broad rule above a narrow one and the narrow one never fires. For example, WHEN weight >= 300 THEN 'Heavy' placed first would label every row “Heavy,” and no row would ever reach “Texas.” Order rules from most specific to most general.
4 · COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)
ExpressionCountsPlain terms
COUNT(*) / COUNT(1)every row in the group“How many rows?”
COUNT(weight)rows where weight IS NOT NULL“How many rows have a value here?”
COUNT(DISTINCT player_name)unique non-null values“How many different players?” (protects against duplicate rows)
5 · Non-sargable filters disable indexes and pruning
Plain: if you wrap the column in a function or calculation, the engine has to compute it for every row before it can compare, so it can't jump straight to the matches.
Tech: WHERE weight >= 300 is sargable (index- and pruning-friendly). WHERE weight * 1.0 >= 300 or WHERE CAST(weight AS TEXT) … is not. The same applies to dates: prefer WHERE d >= '2026-01-01' AND d < '2027-01-01' over WHERE EXTRACT(YEAR FROM d) = 2026.
6 · Filter rows in WHERE, not HAVING
HAVING state = 'TX' is either invalid or wasteful. HAVING runs after grouping, so the engine aggregates rows it will then discard. Row conditions belong in WHERE (filter early). Conditions on aggregates (HAVING COUNT(*) >= 3) belong in HAVING.
7 · No ORDER BY = no guaranteed order
Results that “always came back sorted” in development can change when data grows, the engine upgrades or the plan switches to parallel. Tests and snapshot diffs that depend on row order become flaky. Always ORDER BY when order matters.

9 · The production version

Plain terms: the original query is fine for a one-off answer. In a pipeline that runs daily, other people read it, it feeds dashboards, and data changes underneath it. Production SQL is written so it's readable, testable, reusable and safe to change. Here's the same logic, rebuilt the way an Analytics Engineer would ship it in dbt.

Pattern A · Layered CTEs (import → logic → final)

Plain: break the query into named steps that read top to bottom in the same order the engine evaluates them. To debug, change the last line to select * from <any step>.
Tech: dbt Labs' convention is import CTEs named after their source, logical CTEs with descriptive names, and a final select * from final. Modern optimizers inline CTEs (PostgreSQL ≥ 12 folds them by default), so this is readability with no runtime cost.

Pattern B · Replace hard-coded CASE with a mapping table

Plain: instead of burying “CA, OR, WA = West Coast” inside one query, keep it in a small lookup table. When the business adds Nevada, you edit one row in one file, and every query that uses regions updates.
Tech: the mapping becomes a dbt seed (version-controlled CSV) joined with a LEFT JOIN plus COALESCE for the default. This gives you a single source of truth and makes the mapping itself testable. Watch out: a duplicate state in the seed makes the join fan out (one player matches two rows) and silently double-counts. That's why the seed gets a unique test.

models/marts/heavy_players_by_region.sql

{# threshold is a project var, not a magic number #}
{% set min_weight_lbs = var('heavy_player_min_weight_lbs', 300) %}

with players as (
    select * from {{ ref('stg_benn__college_football_players') }}
),

state_region_map as (
    select * from {{ ref('state_region_map') }}
),

heavy_players as (                    -- step 2: filter early
    select state_code
    from players
    where weight_lbs >= {{ min_weight_lbs }}
),

labeled as (                          -- step 3: label via lookup
    select
        case
            when heavy_players.state_code is null then 'Unknown'
            else coalesce(state_region_map.region, 'Other')
        end as region
    from heavy_players
    left join state_region_map
        on heavy_players.state_code = state_region_map.state
),

final as (                            -- steps 4–6
    select
        region,
        count(*) as player_count
    from labeled
    group by 1
)

select * from final

Pattern C · Tests that prove the result is right

Plain: automated checks that run on every build and fail loudly when something's off, instead of a stakeholder noticing a wrong number weeks later.
Tech: generic tests in YAML (not_null, unique, accepted_values) plus a singular test for reconciliation, the SQL version of the control total you already run on 1099 data.

models/marts/_marts.yml

models:
  - name: heavy_players_by_region
    description: Count of players at/above the weight threshold, by region.
    columns:
      - name: region
        data_tests:
          - not_null
          - unique                   # grain = one row per region
          - accepted_values:
              values: ['West Coast', 'Texas', 'Other', 'Unknown']
      - name: player_count
        data_tests: [not_null]

seeds:
  - name: state_region_map
    columns:
      - name: state
        data_tests: [not_null, unique]  # prevents join fan-out

Test-argument syntax has been evolving across recent dbt versions. Check the docs for the version pinned in your project.

-- Returns rows only when totals disagree → test fails.
with expected as (
    select count(*) as n
    from {{ ref('stg_benn__college_football_players') }}

10 · Run it yourself (Jupyter + DuckDB in VS Code)

One notebook cell. It recreates the sample, runs the query, and prints the plan so you can map each operator to steps 1–6. Install with uv add duckdb.

import duckdb

con = duckdb.connect()  # in-memory database

con.sql("""
    CREATE TABLE college_football_players AS
    SELECT * FROM (VALUES
        ('Leo','CA',310), ('Mia','TX',295), ('Sam','WA',320), ('Ana','TX',305),
        ('Ben','FL',330), ('Kai','OR',302), ('Zoe','TX',315), ('Max','NY',300),
        ('Eli','CA',290), ('Ray','GA',340), ('Jo','TX',260),  ('Tom','OH',312),
        ('Ned', NULL, 305),   -- edge case: NULL state  → which region?
        ('Gus','tx', 318)     -- edge case: dirty value → which region?
    ) AS t(player_name, state, weight)
""")

query = """
    SELECT CASE WHEN state IN ('CA', 'OR', 'WA') THEN 'West Coast'
                WHEN state = 'TX' THEN 'Texas'
                ELSE 'Other' END AS arbitrary_regional_designation,
           COUNT(1) AS players
      FROM college_football_players
     WHERE weight >= 300
     GROUP BY 1
     ORDER BY players DESC
"""

con.sql(query).show()                         # result
print(con.sql("EXPLAIN " + query).fetchall()[0][1])          # physical plan
print(con.sql("EXPLAIN ANALYZE " + query).fetchall()[0][1])  # with actual timings
Predict before you run
With Ned (NULL) and Gus ('tx') added, “Other” becomes 6 instead of 4 (verified: Other 6 · West Coast 3 · Texas 2), so two players were silently mislabeled with no error. Then wrap state in upper(trim(state)) and add a WHEN state IS NULL branch, and check that Gus moves to Texas and Ned to Unknown.

11 · Recall & practice

From → Where → Group by → Having → Select → Order by → Limit
“First We Gather, Handpick, Show, Organize, Limit.” Filters before groups, groups before output, output before sorting.

Easy

Add ORDER BY players DESC. Why can ORDER BY use the alias players when WHERE can't? Answer it using the logical order table.

Medium

Add a 'Florida' region. Where in the CASE must it go? With the 12-row sample, what are the new counts? (West 3 · Texas 2 · Florida 1 · Other 3.)

Hard

Return AVG(weight) per region, only for regions with ≥ 3 heavy players, sorted descending. Predict which groups survive HAVING before you run it, then confirm with EXPLAIN.
